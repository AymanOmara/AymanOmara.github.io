CASE STUDY · RESERVATIONS · KUWAIT · FLUTTER

Two booking apps, taken over and shipped as three brands.

Hojozat lets people in Kuwait book chalets and clubs, and lets owners manage those bookings. I took over both Flutter apps, the customer app and the owner app, rebuilt how booking and payment work, connected the two with QR check-in, and turned the customer app into three branded apps.

Starting point

Both apps came to me as an agency’s working codebase, already booking chalets. From there I made 80 of 81 commits to the customer app and 37 of 38 to the owner app, rewriting most of the booking and payment code along the way.

What I built

  • An availability calendar, written from scratch: it loads availability month by month, caches the months it has seen, and blocks past and unavailable days.
  • Reservations and payment, rebuilt: pricing with insurance and discounts, a choice of payment method, split payments with a share link, and cancelling the booking if payment fails.
  • Server-driven client forms: the API decides which of about 19 fields (civil number, passport, address and more) each club shows and requires, and the form builds itself from those rules.
  • Push notifications in both apps. Tapping one in the owner app opens the reservation it’s about.
  • QR check-in on both sides, booking on a customer’s behalf from the owner app, and free reservations that skip payment.

Code from the apps

Four kinds of booking share one flow: by the hour, a range of days, packages and events. The request builder adds dates or time slots depending on the club’s type, and the owner app confirms a check-in by sending back the secret from the customer’s QR code.

Map<String, dynamic> createReservationRequest() {
  var data = {
    "club_id": clubData?.id?.toString() ?? "",
    "payment_method": state.selectedPaymentMethod.value.title,
    "reservation_type": clubData?.reservationType ?? "",
    "participants_number": state.selectedPaymentMethod.value == PaymentMethod.SHARED
        ? state.personsCount.value : "1",
    "payment_gateway": state.selectedPaymentOption?.value.paymentGetWayId,
    "client_data": { "primary_phone_number": reservationData?.phone ?? "", /* …the fields the server asks for */ },
  };
  if (clubData?.reservationType == "days_range" || clubData?.reservationType == "days") {
    data["dates"] = [{"from": reservationData?.selectedDate?.from, "to": reservationData?.selectedDate?.to}];
  } else if (clubData?.reservationType == "hours") {
    data["times"] = reservationData?.times?.map((e) => {"from": e.from, "to": e.to}).toList();
    data["date"] = reservationData?.date;
  }
  return data;
}

A booking, end to end

The QR check-in joins the two apps: I built the customer side that shows the code and the owner side that scans and confirms it.

  1. BookThe customer picks dates on the availability calendar and gets a price from reservations/price.
  2. PayThey pay alone or split the bill; a shared booking returns a link for the others.
  3. QRThe customer’s reservation shows a QR code generated by the server.
  4. ScanAt the chalet, the owner scans it. It carries the club, the reservation and a confirmation secret.
  5. OpenThe owner app jumps straight to that reservation.
  6. ConfirmThe owner confirms, and the app sends the secret back to the API.

A clean rewrite, started

Growing features on an agency template got harder, so I started rewriting the customer app on separate data, domain and di packages: Cubits, use cases, get_it, a single Dio client and a sealed Result type. Login, home, categories, paginated clubs, club details and package bookings work in the rewrite. It hasn’t replaced the live app.
