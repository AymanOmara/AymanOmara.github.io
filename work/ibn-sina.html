CASE STUDY · LEGACY REWRITE · FLUTTER + ASP.NET CORE

Replacing a rejected app, from the API to the admin dashboard.

Ibn Sina sells dental supplies to students and clinics. Its Xamarin app kept getting rejected from the store, even after I fixed its bugs. I rebuilt the customer app in Flutter, built a Flutter web dashboard for the shop, and started the ASP.NET Core API that both use.

The API, in Swagger

One ASP.NET Core API serves both the customer app and the admin dashboard. I started it: the project, the database-first EF Core model and the first controllers. A teammate and I then built it out together. Endpoints I wrote are marked.

Swagger UI recreated from the controllers and models in the repository. The data in the examples is invented.

Code I wrote

Placing an order is two writes: the order row, then one row per product with the price and quantity at the time of purchase. Favourites are a join table read in two queries. Both are EF Core against SQL Server, returning JSON the Flutter clients map into their own models.

[HttpPost("MakeOrder")]
public async Task<ActionResult<Order>> MakeOrder([FromBody] OrderRequest orderRequest)
{
    // Step 1: Create the order
    var order = new Order
    {
        Userid = orderRequest.UserId,
        Ordertime = DateTime.UtcNow,
        Orderstatus = orderRequest.OrderStatus,
        Orderprice = orderRequest.OrderPrice,
        Deliveryfees = orderRequest.DeliveryFees,
        Ordergovernorate = orderRequest.OrderGovernorate,
        // …phone, location, payment method, amount
    };

    _context.Orders.Add(order);
    await _context.SaveChangesAsync();

    // Step 2: Add products to the order
    foreach (var product in orderRequest.OrderProducts)
    {
        _context.Orderprouductlists.Add(new Orderprouductlist
        {
            Orderid = order.Orderid,
            Prouductid = product.ProuductId,
            Price = product.Price,
            Amount = product.Amount
        });
    }

    await _context.SaveChangesAsync();
    return Ok(new { order = order, id = order.Orderid });
}

[HttpGet("GetAllFavorites")]
public async Task<ActionResult<IEnumerable<Prouduct>>> GetAllFavorites(int userId)
{
    var favoritesIds = await _context.Usersprouducts
        .Where(fav => fav.Userid == userId)
        .Select(pr => pr.Prouductid)
        .ToListAsync();

    var products = await _context.Prouducts
        .Where(product => favoritesIds.Contains(product.Productid))
        .ToListAsync();

    return Ok(products);
}

Data model

8 tables in SQL Server, scaffolded database-first with EF Core Power Tools. Order line items keep their own price, so an order still shows what the customer paid after a product’s price changes. Products carry the filters the app offers dental students: study year (first to fifth), clothes and teeth. Delivery fees live in their own table so the dashboard can change them without a release.

An order, end to end

One order touches all three codebases. I built both Flutter apps and the order endpoints; my teammate added the push notification when an order is accepted.

  1. OrderThe customer app sends the cart to MakeOrder: the order row, then a row per product.
  2. ReviewThe dashboard loads GetAllOrders and each order’s products into a data grid.
  3. AcceptAn admin accepts the order, and the dashboard calls EditOrder with the status Accepted.
  4. NotifyThe API saves a notification for the customer.
  5. PushFirebase Cloud Messaging (HTTP v1) delivers it to the customer’s phone.
  6. TrackThe app shows it under notifications, and the order under history.

The apps

  • Customer app (Flutter): a home banner slider, products by category with the study-year filters, product details, cart, checkout with the governorate and payment method, order history, notifications, and account sign-up, login and deletion.
  • Admin dashboard (Flutter web): products in a data grid with add and edit forms, orders with their line items and an accept action, creating orders for customers, delivery fees, notifications, and PDF invoices with Arabic text.
  • Both on separate common, domain, data and di packages, with a Cubit per screen, get_it and Dio, in Arabic and English.

What I’d do next

The API was built fast to replace a rejected app, and it shows. These are the changes I’d make before it grows:

  • Authentication and roles: JWT with separate customer and admin roles, so only the dashboard can manage products and orders.
  • Hashed passwords with ASP.NET Core Identity, and a login response that returns a token instead of the user record.
  • A service layer between the controllers and EF Core, with request validation and one response envelope on every endpoint.
  • Real foreign keys and migrations, and an order status that’s an enum instead of free text.
